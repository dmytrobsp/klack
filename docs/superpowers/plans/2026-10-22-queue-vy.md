### Task 1 (VY1): Activity "unread only" filter — the bug and remembering it (items 2 and 3)

The user: "in activity view `unread only` filter behaves weird. the first time i enabled it the app showed me all
unseen activity from `all` tab. when i pressed enter on one of the entries to check it out and then went back to
activity view - the `unread only` filter on `all` tab showed nothing e.g. 'Nothing unread here.'. And only when i
switched to threads tab did it show me the rest of the entries again." and "the activity view should remember the
state of `unread only` filter. meaning if i turned it on one - it stays on until i turn it off. no need to persist it
between app launched, simple in-memory persistence will do".

- Find the root cause first (superpowers:systematic-debugging): reproduce it in a test from the real flow (open
  Activity, `u`, Enter on an item, open Activity again, `u`), and live on rslack-testbed (B mentions A a few times in
  different places; A opens Activity). Candidates to check, not conclusions: what `activity.markRead` with the item's
  `ts` does to the other items on Slack (marks everything up to it?), `apply_seen` / the `seen` map marking more than
  the opened item, the All tab's list kept from before vs loaded again, `is_unread` in a reloaded page.
- Fix it so the All tab with the filter shows exactly what is still unread (as the Threads tab did), then the ruling
  for item 3.
- Tests that pin both: the reported sequence, and the filter kept across leaving/reopening and tab switches.

### Task 8 (VY8): Threads feed — edits, deletions and reactions live

Follows from the user's item 4 ("how does the original app behave? if its similar … keeping it as is") and the
observation of Slack's web client (2026-10-22): its Threads view applies replies, edits and reactions to listed threads
